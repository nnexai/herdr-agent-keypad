# Phase 03.1: Code Review Report

**Reviewed:** 2026-08-21T13:45:45Z  
**Depth:** standard  
**Files Reviewed:** 26  
**Status:** issues_found

## Summary

The review covered the Phase 03.1 firmware scheduler/projection/rendering changes, LED grammars, menu path, capture/protocol contracts, and exact-device evidence runner. Four release-blocking paths remain: a valid legacy metrics reply crashes protocol classification; physical acceptance does not retain or enforce the Phase 03.1 metrics that establish its timing/resource claims; accumulated encoder deltas skip the required one-detent interaction model; and the LED event clock is not connected to focus feedback. The display-side pending phase carrier is also dropped before rendering.

## Critical Issues

### CR-01: Accepted legacy `metrics_ack` crashes the frame classifier

**File:** `tools/phase1_bringup/src/phase1_bringup/protocol.py:126-134,181-182`  
**Issue:** `validate_frame()` explicitly accepts the legacy 15-field `metrics_ack` shape at lines 126-134, then unconditionally indexes every field in the newer 29-field `PAYLOAD_KEYS["metrics_ack"]` set at line 181. A legacy frame therefore raises an uncaught `KeyError`, not a typed `ProtocolError`; `classify_line()` only catches `ProtocolError` around this call (`protocol.py:214-218`). A connected stale or malformed peer can terminate the bridge/evidence path rather than being rejected cleanly.

**Fix:** Make the protocol version/shape unambiguous. For Phase 03.1 metrics, remove legacy acceptance and require the full set in both the Python validator and `protocol/schema/v1.json`. If compatibility is required, validate exactly the selected shape without indexing fields that are absent, then return a typed incompatibility result to callers that require Phase 03.1 evidence.

### CR-02: Exact-device acceptance discards and never validates required timing/resource metrics

**File:** `tools/phase1_bringup/src/phase1_bringup/phase3_smoke.py:1518-1530,2106-2110`  
**Issue:** `_phase31_machine_metrics()` fetches `metrics_ack` but retains only six legacy counters. It drops `compose_flush_max_us`, `animation_duty_max_percent`, `allocation_stable`, both first-response metrics, degradation/cadence counters, and reveal timing—the measurements Phase 03.1 uses to establish the 30% duty, input-latency, allocation, and degradation invariants. `validate_phase31_device_evidence()` subsequently accepts any machine record whose nested `status` is `pass`; it never requires the full metric shape or checks its values. As a result, a device-evidence artifact can pass with no persisted proof that the mandatory resource/input constraints were met.

**Fix:** Parse the response through `_phase31_metrics()` and persist the complete metric set. In `validate_phase31_device_evidence()`, require that complete set for every machine observation and reject non-passing allocation stability, hard-ceiling violations, or missing/nonzero observations required by the physical-acceptance contract. Update the JSON-schema `metrics_ack.required` list to the same complete set so generic schema consumers cannot accept a reduced payload.

### CR-03: Batched encoder deltas coalesce multiple detents into one menu mutation

**File:** `firmware/src/app/menu_controller.cpp:144-185`  
**Issue:** `MenuController::rotate()` applies the raw magnitude of `delta`: root navigation adds `delta` at line 149, theme/grammar selection adds `delta` at lines 162/168, and brightness applies `delta * 10` at line 174. The main loop passes the unexpanded hardware delta from `ProductInputRouter` into this method (`firmware/src/main.cpp:669-674`). When the encoder is turned faster than a polling interval, an accumulated delta can skip several rows or jump brightness by multiple 10% steps in one input turn. This violates the specified one-detent/one-row-or-value causal behavior and the explicit prohibition on coalescing.

**Fix:** Expand a bounded accumulated delta into individual signed detent actions in the input router (while retaining agent-slot precedence), or make `rotate()` consume exactly one signed step and retain remaining detents in fixed bounded storage. Render and apply brightness for each accepted detent rather than collapsing all steps into one state transition.

### CR-04: LED feedback has no shared semantic event clock after the initial generation transition

**File:** `firmware/src/app/agent_projection.cpp:906-929,944-965`; `firmware/src/ui/led_engine.cpp:104-118`; `firmware/src/ui/led_grammar_field_ext.cpp:43-51`  
**Issue:** `semantic_event_epoch_` is set only when a snapshot is committed (`agent_projection.cpp:528,572`); neither a press nor an admitted focus result advances it. `LedEngine::render()` then derives its event phase from `state.transition_phase` when the caller does not provide an event (`led_engine.cpp:104-118`). That transition phase belongs to the last ordinary snapshot and returns to zero after 200 ms, not to the press/pending/success/failure event. Consequently Field Extension's pending branch always selects halo step zero after a normal transition completes (`led_grammar_field_ext.cpp:43-51`) instead of the required 0→1→2 sweep. The same stale phase makes Rail Echo and Exception Channel feedback pulses stop or remain at a fixed phase.

**Fix:** Create an explicit, bounded semantic-event epoch/start time when a press, pending step, focus result, health/fence, or menu event is admitted. Carry its event-relative phase through `RenderState`/`LedEvents`, and make grammars consume that phase. Preserve the central immediate SYNC/health override, but do not fall back to unrelated snapshot-transition progress for feedback.

## Warnings

### WR-01: Projection updates a pending phase that no renderer can observe

**File:** `firmware/src/app/agent_projection.cpp:721-724`  
**Issue:** The projection increments `feedback_phase_[slot]` at each 300 ms pending deadline, but neither `renderTileAt()` (`firmware/src/app/agent_projection.cpp:650-700`) nor `renderState()` (`agent_projection.cpp:852-903`) assigns it to `RenderState::Slot::feedback_phase`. The theme renderers instead derive pending decoration from ambient or transition phase. This makes the dedicated pending cadence dead state and allows unrelated ambient cadence/degradation to determine its visuals.

**Fix:** Materialize `feedback_phase_[slot]` in both RenderState construction paths and use `tile.feedback_phase` for pending feedback geometry. Add an observable render-log test that proves successive pending deadlines advance the theme-local cue independently of ambient phase.
