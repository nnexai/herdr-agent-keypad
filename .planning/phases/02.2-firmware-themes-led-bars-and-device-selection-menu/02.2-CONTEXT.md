# Phase 02.2: Firmware Themes, LED Bars, and Device Selection Menu - Context

**Gathered:** 2026-08-18
**Status:** Ready for planning, with two explicit contract reconciliations required before implementation

<domain>
## Phase Boundary

Deliver four selectable firmware display languages—Signal Edge, Ledger, Beacon, and Instrument—plus four independently selectable 14-pixel LED grammars and a bounded encoder settings menu. The menu in this phase selects and persists only display theme and LED grammar; truthful Codex values, full device-health diagnostics, and brightness controls remain Phase 3. Preserve host-authoritative snapshots, exact generation-bound focus-only actions, independent freshness truth, bounded device data, and the existing firmware/board/protocol seams.

The user also requested two changes that conflict with existing locked contracts and MUST be reconciled before implementation: continuous theme-specific ambient animation, and atomic-per-panel progressive reveal rather than one logical all-panel generation. These are recorded as intentional decisions, not silently normalized away.

</domain>

<decisions>
## Implementation Decisions

### Theme contracts
- **D-01:** Implement four faithful display languages, not four color skins: Signal Edge uses the state rail, Ledger uses the typographic inbox row, Beacon uses the large state glyph/field, and Instrument uses the ring/gauge vocabulary. Shared normalized semantics remain identical across themes.
- **D-02:** Each theme must budget its complete information hierarchy for native 128×128 panels. Long text may be cut off with ellipses or bounded abbreviations; theme-specific hints and truncation are expected. Do not shrink below the agreed text floor or redesign the theme dynamically to accommodate arbitrary strings.
- **D-03:** Signal Edge is the safe default after first boot or invalid stored theme data.
- **D-04:** Theme selection previews before commit. Because the settings menu changes visual style with the theme, selecting a theme previews the menu style and requires encoder click to confirm. The usage screen is not previewed.

### LED grammars
- **D-05:** Theme and LED grammar are independent settings. All 16 theme/grammar combinations are valid; grammars consume shared normalized state rather than theme-specific pixels.
- **D-06:** LED meanings use dedicated physical zones and deterministic overlays. Per-key state remains in its mapped zone; usage owns its usage zone; health owns its documented health zone; menu-open owns the encoder indication; transient focus feedback overrides only its mapped grammar zone.
- **D-07:** Use the proposal brightness ladders as defaults rather than hard caps because the delivered 14-pixel base hardware is not the future expanded multi-screen/LED configuration. Research must still measure safe values on the real unit and retain bounded global brightness, dim, and all-off controls; raw unbounded LED values are not acceptable.
- **D-08:** Every grammar provides a bounded, grammar-specific LED cue for pending, exact-focus success, and failure/uncertain outcomes. Success/failure feedback is finite and never causes retries.

### Menu and persistence
- **D-09:** Phase 02.2's real encoder menu contains theme and LED grammar settings only. The full truthful Codex/device-health/brightness menu remains Phase 3.
- **D-10:** Use a panel-4 menu overlay. Encoder click opens/closes it; rotation moves a bounded cursor; click enters or confirms the highlighted setting. Agent keys 1–3 remain live direct focus paths while the menu is open.
- **D-11:** Persist only explicitly confirmed display theme and LED grammar. Preview selections are volatile. Host snapshots, inbox order, generation-bound identities, freshness, and focus semantics are never persisted on the device.
- **D-12:** Clamp encoder navigation at the first and last menu rows. Invalid or unavailable stored values fall back to Signal Edge plus a safe LED default and are not considered user confirmation.

### Motion and feedback
- **D-13 — contract conflict:** The user selected theme-specific ambient motion rather than the current BLOCKED-only/no-decorative-motion rule. Treat this as an intentional scope request that conflicts with the project's current anti-feature and the design proposal's shared motion charter. The planner must reconcile requirements and acceptance scope before implementation.
- **D-14 — contract conflict:** The user selected continuous frame animation rather than bounded discrete keyframes. This conflicts with Phase 02.1's measured compose-then-flush resource model. Research/planning must establish a real-device frame-time, memory, power, and flicker budget before accepting continuous animation.
- **D-15:** Focus feedback should remain snappy and brief: pending appears immediately; exact success holds approximately 800 ms then returns to the current resting state; failure-family outcomes remain until a newer generation or bounded timeout.
- **D-16 — contract conflict:** The user clarified that each panel should be composed/flushed atomically, but panels may reveal their new state independently. This permits a short mixed-generation window and conflicts with Phase 02.1/SYNC-02's all-panel logical-generation invariant. The planner must explicitly decide whether to amend SYNC-02/02.1 assumptions or preserve the prior invariant before implementation.

### Contract reconciliation required before implementation
- The requested continuous ambient animation must be reconciled with `.planning/REQUIREMENTS.md`'s out-of-scope decorative animation rule, the design proposal's BLOCKED-only motion charter, and Phase 02.1's compose-then-flush measurements.
- The requested per-panel progressive reveal must be reconciled with `.planning/REQUIREMENTS.md` SYNC-02 and `.planning/phases/02.1-reliable-live-synchronization-focus-and-flicker-free-renderi/02.1-CONTEXT.md`'s one-logical-generation display/binding invariant.

### the agent's Discretion
- Preserve existing protocol field names, BoardAdapter/PhysicalMap boundaries, bounded buffers, native-test conventions, and exact host authority/focus semantics while implementing the decided visual behavior.
- Choose the concrete safe LED default, menu row labels, truncation algorithm, primitive geometry, and theme-specific feedback choreography once research validates the physical display and LED behavior. These choices must not alter the decisions above.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `AgentProjection` already stages and validates three agent slots, carries tile state and focus bindings, tracks feedback, and commits through `BoardAdapter`; themes should render from this state rather than add a second snapshot cache.
- `BoardAdapter` already centralizes the official LILYGO abstraction, sequential display access, ButtonSense key polling, encoder delta/click mapping, brightness, and logical LED masks.
- `PhysicalMap` is the accepted source for four panels, five keys, encoder click, and all 14 LED indices.
- Existing native PlatformIO tests provide a low-cost seam for renderer state transitions, generation replacement, null-panel failure, and feedback reset.

### Established Patterns
- Host sends bounded full snapshots; firmware does not reorder agents, synthesize priority, or own focus policy.
- Keys 1–3 capture the displayed opaque identity and generation; menu/encoder input is separate from direct focus.
- Panel access is sequential through the official board wrapper. The existing Phase 02.1 renderer uses a reused PSRAM-preferred RGB565 composition buffer and commit fencing.
- Evidence and protocol changes must stay bounded, redacted, and compatible with the pinned native/selected-USB environments.

### Integration Points
- `firmware/src/main.cpp` must replace or coexist cleanly with the temporary bring-up render path for normal runtime, while preserving protocol admission and `reportAgentKey()` focus behavior.
- `AgentProjection` needs a shared render-state/theme seam and a panel-4/menu surface without changing host snapshot or focus payloads.
- `BoardAdapter::setLeds()` and `PhysicalMap::ledMask()` are the only safe LED output path; theme-independent LED grammars should consume logical masks and bounded HSV/brightness values.
- Encoder polling (`encoderDelta()` plus mapped click) must drive menu state without disabling `BoardAdapter::wasPressed()` for keys 0–2.
- Persistence must live inside the approved device-settings boundary and must not persist host data or action bindings.

</code_context>

<specifics>
## Specific Ideas

- The intended visual direction is four genuinely different languages, not cosmetic recoloring: Signal Edge's rail, Ledger's typographic density, Beacon's distance-first field, and Instrument's ring/gauge vocabulary.
- Long labels are expected to truncate with ellipses or bounded abbreviations rather than force smaller unreadable text.
- Theme preview applies to the settings menu and waits for encoder confirmation; the usage screen is not part of the preview.
- The settings menu is a panel-4 overlay and the three agent keys remain direct/live while it is open.
- LED grammars are independently combinable with themes and must provide their own bounded focus feedback.
- User preference: keep focus feedback snappy and brief.

</specifics>
