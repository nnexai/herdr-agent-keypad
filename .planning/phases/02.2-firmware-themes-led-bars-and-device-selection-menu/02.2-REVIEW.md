# Phase 02.2 code review report

**Reviewed:** 2026-08-20T15:54:49Z
**Depth:** standard
**Files reviewed:** 26
**Status:** issues_found

## Summary

The review covered the Phase 02.2 firmware rendering, animation, settings, LED, menu, runtime integration, native test, and smoke-driver files named by the plan summaries. Six actionable defects remain. They affect persistence atomicity, fail-closed presentation, two required LED/fence states, and the integrity of exact-device smoke evidence. No physical fallback deferral is reported here because it is accepted verification debt, not a source defect.

## Narrative findings (AI reviewer)

### Warnings

#### WR-01: A failed settings write can persist a valid but unintended theme/grammar pair

**Severity:** WARNING

**File:** `firmware/src/app/settings_store.cpp:36-38`

**Issue:** `confirm()` writes `ver`, then `theme`, then `ledgram` and reports failure if any call fails. If an existing valid record is present and the final write fails or power is lost after the theme write, `load()` later sees schema v1 and two in-range enum values. It accepts the new theme paired with the old grammar as a valid selection. This violates confirmation-only persistence because the user never confirmed that hybrid pair.

**Evidence:** `load()` validates only key presence, schema version, and enum ranges at `firmware/src/app/settings_store.cpp:17-28`; it has no transaction marker or record generation to distinguish a complete record from a partial update.

**Fix:** Invalidate the committed marker before replacing either value, write both enum values, then write `ver = kSchemaVersion` last. A reset or failed write then produces the documented safe fallback rather than a hybrid valid record. Add a native failure-injection test for each individual `put*` failure and for interruption after each write.

#### WR-02: A failed confirmed-theme redraw leaves the renderer switched after a partial cluster repaint

**Severity:** WARNING

**File:** `firmware/src/main.cpp:532-540`; `firmware/src/app/agent_projection.cpp:337-342`

**Issue:** `refreshMenuPresentation()` installs the newly stored renderer before calling `redrawTiles()`. `redrawTiles()` flushes panels one by one and returns immediately on a failed panel. On failure, `presentedTheme` stays old, but `AgentProjection::theme_` remains new and panel 4 is rendered with the new theme. Later state updates use the new renderer for individual panels. The display can therefore remain a mixed-theme cluster after a failed confirmed change, rather than entering a safe synchronized state.

**Evidence:** Unlike snapshot commits, which disable bindings and render SYNC on a mid-reveal failure at `firmware/src/app/agent_projection.cpp:232-256`, the redraw path has no rollback or fail-closed branch.

**Fix:** Make confirmed theme redraw a transactional projection operation. Compose and flush all three agent panels with the candidate renderer, and on any failure render SYNC and deactivate bindings, or restore the prior complete theme before returning failure. Only change the active renderer and `presentedTheme` after all three panel pushes succeed. Add a native missing-panel test for this path.

#### WR-03: Field Extension omits the required menu indicator and health pulse

**Severity:** WARNING

**File:** `firmware/src/ui/led_grammar_field_ext.cpp:47-52, 79-80`

**Issue:** The grammar discards `LedEvents`, so opening the menu never lights L13. Its health branch emits a constant red pair and returns without using time, so L12-L13 do not breathe. The Field Extension contract requires L13 while the menu is open unless health owns the pair, and a dim red health pulse on the pair.

**Evidence:** The unused parameter is declared at line 47. The health output at lines 50-52 is always brightness 10, and the normal path ends at line 80 without emitting a menu segment.

**Fix:** Name and consume `events`; append an L13 menu segment after normal slot segments when `events.menu_open` is true. Derive health brightness from `now_us` using the shared blocked half-period or another documented pulse phase, keeping its peak at 10. Extend `test_led_grammar_scene_masks` with Field Extension menu and health-phase assertions.

#### WR-04: Beacon and Instrument suppress source-health fencing on empty panels

**Severity:** WARNING

**File:** `firmware/src/ui/theme_beacon.cpp:159-172`; `firmware/src/ui/theme_instrument.cpp:166-171`

**Issue:** Both renderers return immediately for `TileState::Empty`. That bypasses Beacon's source-fence line and literal reason at lines 214-220, and Instrument's literal reason at lines 208-211. During STALE, OFFLINE, or UNAVAILABLE snapshots with an empty slot, those panels look like ordinary empty slots instead of visibly fenced source data.

**Evidence:** Signal Edge and Ledger handle their empty state without bypassing their final feedback/fence layer, so they still show the health reason. The two early returns prevent the equivalent code from running in Beacon and Instrument.

**Fix:** Keep the empty anatomy, but render the source-health fence after it. Beacon should add its bottom reason band and OFFLINE hairline; Instrument should retain red bezel ticks and add the literal reason in its reserved meta line. Add empty-slot fence cases to `assertThemeVocabulary`.

#### WR-05: The smoke driver bypasses bounded, authenticated session framing and accepts arbitrary serial responses as evidence

**Severity:** WARNING

**File:** `tools/phase1_bringup/src/phase1_bringup/phase22_smoke.py:152-205, 253-256`

**Issue:** `DeviceSession` parses arbitrary JSON from the serial stream, has no maximum buffered-line size, and treats a matching `reply_to` as a response without validating the envelope, digest, boot ID, session ID, sequence, or allowed response type. `send()` also ignores the return value of `connection.write()`. A noisy, stale, truncated, or spoofed serial response can be recorded as a successful snapshot or metrics fact, and an unterminated input can grow `_rx_buffer` without limit.

**Evidence:** The existing shared `SerialLink` bounds reads and rejects oversized lines in `tools/phase1_bringup/src/phase1_bringup/serial_link.py:148-181`. Its `ProtocolSession` validates frame digest, boot/session identity, ordering, response type, and full writes in `tools/phase1_bringup/src/phase1_bringup/protocol.py:447-519`. Plan 05 explicitly required the new driver to reuse that plumbing.

**Fix:** Replace the bespoke `DeviceSession` transport with `SerialLink` plus the existing v1/v2 `ProtocolSession` flow, or provide an equivalent implementation that enforces the same line cap, complete-write check, digest validation, identity binding, sequencing, and response-type allowlist. Bind the hardware run to the paired device identity before recording evidence. Add tests for an oversized unterminated frame, short write, mismatched session/boot, bad digest, and a stale matching `reply_to`.

#### WR-06: Smoke evidence and its checksum can be left inconsistent after interruption

**Severity:** WARNING

**File:** `tools/phase1_bringup/src/phase1_bringup/phase22_smoke.py:134-139`

**Issue:** `SmokeEvidence.write()` overwrites the JSON file directly and then writes its checksum in a separate operation. A process interruption, full filesystem, or write error can leave a truncated evidence file, a new JSON with an old checksum, or a valid JSON without a matching checksum. The acceptance record is then neither immutable nor hash-addressable.

**Evidence:** The project already provides fsync-and-replace persistence in `tools/phase1_bringup/src/phase1_bringup/evidence.py:498-518`, but the Phase 02.2 driver does not use it.

**Fix:** Serialize once, write the evidence and checksum through atomic temporary-file replacements with file and directory fsync, and verify the final checksum after both replacements. Reuse the existing atomic helper or expose a small public wrapper for this paired artifact operation. Add an error-injection test that proves a failed replacement never reports a completed evidence record.
