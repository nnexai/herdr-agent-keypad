## Gesture intent boundary

### Hold timing

| Option | Description | Selected |
|--------|-------------|----------|
| Balanced 500–600 ms | Distinct from a normal tap without making push-to-talk sluggish; exact value finalized from physical measurements. | ✓ |
| Fast 350–450 ms | More responsive, with a narrower margin against accidental holds and debounce variance. | |
| Conservative 700–800 ms | Stronger accidental-activation protection, with a noticeable delay before voice input. | |

**User's choice:** Balanced 500–600 ms.
**Notes:** Final exact threshold remains subject to physical validation.

### Slow focus acknowledgment

| Option | Description | Selected |
|--------|-------------|----------|
| Wait for existing focus result | Stay armed while physically held, use the existing 3-second focus deadline, and emit Space if the matching success arrives before release. | ✓ |
| Use a shorter hold deadline | Fail the hold after roughly 1 second even if focus may complete later. | |
| Require a fresh hold | Treat a gesture whose acknowledgment misses the threshold as focus-only and require another hold. | |

**User's choice:** Wait for existing focus result.
**Notes:** No second hold-specific timeout policy.

### Threshold consistency

| Option | Description | Selected |
|--------|-------------|----------|
| One shared threshold | Validate one fixed threshold against all three keys and use the worst-case safe value. | ✓ |
| Per-key thresholds | Calibrate each key separately, allowing identical gestures to arm at different times. | |

**User's choice:** One shared threshold.
**Notes:** Consistency across the three direct agent keys is preferred over tighter per-key tuning.

### Timing origin

| Option | Description | Selected |
|--------|-------------|----------|
| Debounced physical press edge | Gesture duration follows the user's finger and existing latched input timestamp, independent of render or CDC delays. | ✓ |
| Focus-intent transmission | Start after firmware sends focus, making perceived timing depend on device workload. | |
| Focus acknowledgment | Start after focus succeeds, adding focus latency to every voice gesture. | |

**User's choice:** Debounced physical press edge.
**Notes:** The threshold is a physical-gesture contract, not a transport-latency contract.

## Overlapping key gestures

### Another key during active Space

| Option | Description | Selected |
|--------|-------------|----------|
| Focus normally; keep original owner | The second key performs exact focus but cannot acquire Space; the original physical key remains owner. | ✓ |
| Ignore other agent keys | Avoid overlap by breaking direct focus while Space is active. | |
| Transfer Space ownership | Move ownership after the new key focuses, creating an ambiguous release boundary. | |

**User's choice:** Focus normally; keep original owner.
**Notes:** Active Space survives later focus changes as a physical keyboard state.

### Another key while Space is pending

| Option | Description | Selected |
|--------|-------------|----------|
| Newest press wins | Cancel the older hold candidate and let only the newest continuously held key acquire Space after its own acknowledgment. | ✓ |
| First held key wins | Keep the original candidate even if focus moves to the second key. | |
| Cancel all hold candidates | Keep both presses as focus actions but require a clean later hold for Space. | |

**User's choice:** Newest press wins.
**Notes:** Each focus action still uses normal exact correlation; only HID eligibility is superseded.

### Same-poll chord

| Option | Description | Selected |
|--------|-------------|----------|
| Chord is focus-only | Preserve focus handling but arm no Space candidate until every agent key releases and a clean single-key gesture begins. | ✓ |
| Deterministic slot wins | Use fixed slot order to choose a hold candidate, even if that does not match intent. | |
| Either may win by acknowledgment | Let result timing determine ownership. | |

**User's choice:** Chord is focus-only.
**Notes:** Ambiguous simultaneous input fails closed for HID without disabling exact focus actions.

### Ownership handoff

| Option | Description | Selected |
|--------|-------------|----------|
| No automatic inheritance | Space-up occurs when the owner releases; another held key must be released and pressed again to begin a new hold. | ✓ |
| Arm held second key | Allow a still-held second key to acquire Space without a new press edge. | |
| Transfer without Space-up | Keep Space continuously down and change the owning key. | |

**User's choice:** No automatic inheritance.
**Notes:** Every Space owner begins with a fresh unambiguous single-key press.

## Hold-state feedback

### Relationship to focus feedback

| Option | Description | Selected |
|--------|-------------|----------|
| Layer hold cues onto focus states | Preserve press/pending/success/failure meaning and add threshold-waiting and active-Space cues. | ✓ |
| Use separate full hold states | Replace focus presentation with full ARMED, ACTIVE, CANCELLED, and FAILED screens. | |
| Use LEDs only for hold | Leave tiles unchanged and show all hold status only in LED zones. | |

**User's choice:** Layer hold cues onto focus states.
**Notes:** User explicitly requested a microphone or similar cue.

### Armed-to-active mic progression

| Option | Description | Selected |
|--------|-------------|----------|
| Outlined/pulsing to solid | Restrained outlined or pulsing mic while armed; immediate solid persistent mic and mapped LED cue once HID is active. | ✓ |
| Dim to bright | Use one static mic at different brightness levels. | |
| Mic only when active | Show no threshold-reached state while waiting for focus. | |

**User's choice:** Outlined/pulsing to solid.
**Notes:** The cue must not imply Space-down before actual HID activation.

### Active owner cue after later focus

| Option | Description | Selected |
|--------|-------------|----------|
| Stay on the owning key | The mic and active LED continue to identify the physical key whose release ends Space. | ✓ |
| Move to newly focused key | Follow application focus even though release ownership remains elsewhere. | |
| Show on every agent tile | Present global Space state on all tiles. | |

**User's choice:** Stay on the owning key.
**Notes:** Ownership visibility takes precedence over following application focus.

### Release before acknowledgment

| Option | Description | Selected |
|--------|-------------|----------|
| Brief crossed-out mic overlay | Show explicit tile cancellation before later focus feedback. | |
| Hold cancel until focus resolves | Keep cancellation visible until focus success, failure, or timeout. | |
| Return directly to focus pending | Remove the hold cue and resume ordinary pending immediately. | ✓ |

**User's choice:** Return directly to focus pending.
**Notes:** This initially conflicted with the roadmap requirement that cancellation remain visibly distinct, so a reconciliation question followed.

### Visible-cancellation reconciliation

| Option | Description | Selected |
|--------|-------------|----------|
| Brief LED-only cancel cue | Tile returns immediately to focus pending while the owning LED zone gives one short grammar-specific cancellation cue. | ✓ |
| Very brief crossed-out mic | Briefly interrupt the tile with a cancelled mic before returning to pending. | |
| Remove visible-cancel requirement | Amend the roadmap criterion so cancellation has no visible cue. | |

**User's choice:** Brief LED-only cancel cue.
**Notes:** Preserves the locked visible-cancellation criterion without delaying normal focus feedback.

## Composite evidence gate

### Pass bar

| Option | Description | Selected |
|--------|-------------|----------|
| All applicable rows pass | One exact paired deployment passes identity/pairing, CDC under HID, ordering, gesture separation, release safety, reconnect, suspend/resume, flashing, and recovery with no open stuck-key defect. | ✓ |
| Pass with documented exceptions | Allow noncritical applicable rows to remain excluded or deferred. | |
| Core path only | Pass only focus, Space-down, and Space-up and defer lifecycle qualification to Phase 4. | |

**User's choice:** All applicable rows pass.
**Notes:** Composite migration cannot begin with unresolved applicable USB lifecycle rows.

### Failure disposition

| Option | Description | Selected |
|--------|-------------|----------|
| After bounded diagnosis and clean retest | Preserve the first failure, classify setup versus product cause, allow one targeted correction, then rerun the affected gate from a clean boot. | ✓ |
| On the first product-looking failure | Stop at the first result that appears to implicate composite USB. | |
| After repeated repair attempts | Continue iterating until confidence is high, making the gate open-ended. | |

**User's choice:** After bounded diagnosis and clean retest.
**Notes:** A reproducible product failure after the clean retest is the recorded failure that may reopen alternatives.

### Stress depth

| Option | Description | Selected |
|--------|-------------|----------|
| Count-based automated stress | Exercise many gesture orders, delayed acknowledgments, overlaps, CDC frames, and lifecycle interruptions; stop on invariant failure. | ✓ |
| Deterministic rows only | Run each named scenario once. | |
| Extended timed soak | Add a fixed long-duration mixed-activity soak. | |

**User's choice:** Count-based automated stress.
**Notes:** Matches the standing preference for automated evidence and avoids a repetitive manual soak.

### HID repeat semantics

| Option | Description | Selected |
|--------|-------------|----------|
| One down state, one up state | Assert Space once, keep it present while held, and release once; host repeat remains outside the device contract. | ✓ |
| Repeated Space press events | Emit repeated taps during the hold. | |
| Suppress all host repeat | Attempt to prevent OS repeat while retaining an ordinary held Space key. | |

**User's choice:** One down state, one up state.
**Notes:** The device must behave as a physical held key, not a repeated macro.
