# Phase 03.2: Focus-Then-Hold USB Keyboard - Pattern map

**Mapped:** 2026-08-21
**Scope:** bounded composite feasibility, production USB migration after PASS, local hold/Space ownership, feedback, qualification, tests, and evidence
**Files classified:** 49 source, test, configuration, and generated-evidence paths or path sets

This phase has a hard sequencing rule. The isolated mode-0 composite prototype and its exact-device gate come first. Production `selected-usb`, discovery, udev, gesture behavior, and feedback change only after a complete composite PASS. A reproducible product failure recorded under D-16 permits a REJECT. A setup or harness failure does not.

**CDC analog:** `firmware/src/transport/usb_cdc.cpp:5-39`

```cpp
void UsbCdcLink::begin(uint32_t baud, size_t receive_capacity) {
  Serial.setRxBufferSize(receive_capacity);
  Serial.begin(baud);
}

size_t UsbCdcLink::write(const uint8_t *source, size_t length) {
  if (source == nullptr || length == 0 || !connected()) return 0;
  size_t written = 0;
  while (written < length) {
    const size_t count = Serial.write(source + written, length - written);
    if (count == 0 || count > length - written) {
      close();
      return 0;
    }
    written += count;
  }
  return written;
}
```

Preserve this full-write and close-on-failure behavior. Do not create another CDC adapter merely because mode 0 maps `Serial` to TinyUSB CDC.

**No repository HID analog:** use the version-matched fallback recorded in `03.2-RESEARCH.md:151-165,270-288`.

```cpp
bool spaceDown();   // one standard keyboard report containing HID_KEY_SPACE
bool releaseAll();  // one empty standard keyboard report
bool ready();       // HID endpoint readiness
```

The public boundary must stay fixed to Space. It must not accept a keycode, string, macro, payload, or generic keyboard operation. The feasibility implementation must also prove this startup order from the official 3.3.11 composite example: register the CDC and keyboard interfaces, begin them, then call `USB.begin()`.

There is no in-repository TinyUSB event callback pattern. Use the official 3.3.11 `ARDUINO_USB_STARTED_EVENT`, `STOPPED`, `SUSPEND`, and `RESUME` APIs cited by research. Keep lifecycle policy in the local controller/HID boundary, not in protocol code.

**One-poll latch:** `firmware/src/board/board_adapter.cpp:43-60`

```cpp
void BoardAdapter::update(uint32_t now_us) {
  if (!ready_) return;
  last_poll_at_us_ = now_us;
  // This is the single poll path for STM32 keys, ButtonSense, and encoder.
  board_.update();
  for (uint8_t logical = 0; logical < PhysicalMap::kKeyCount; ++logical) {
    uint8_t library_index = 0;
    if (physical_map_->keyIndex(logical, library_index) &&
        board_.key(library_index).wasPressed() &&
        (pressed_latch_ & static_cast<uint8_t>(1U << logical)) == 0) {
      pressed_latch_ |= static_cast<uint8_t>(1U << logical);
      key_latched_at_us_[logical] = now_us;
    }
  }
}
```

Extend this loop with cached `isPressed()` and `wasReleased()` truth from the same official `board_.update()` sample. Preserve the first press timestamp until consumption. Same-poll chords must remain visible as one frame rather than being serialized into two pseudo-independent gestures.

**Immediate transition pattern:** `firmware/src/app/menu_controller.cpp:53-66,144-185`

```cpp
void MenuController::close(uint32_t now_us, MenuPresentationCause cause) {
  if (state_.brightness_candidate != state_.brightness_stored) {
    emitBrightness(state_.brightness_stored);
  }
  mode_ = Mode::Closed;
  state_.open = false;
  startPresentation(cause, -1, now_us);
  markDirty();

```

Follow this explicit, fixed-state style. Do not add a gesture queue or heap-backed event list. The hold controller needs one candidate record and one owner record. Its transition table must encode:

- press immediately sends the existing focus intent and records the exact action ID plus physical slot and debounced edge time;
- newest sequential press replaces only the candidate, never earlier focus actions;
- two keys first seen down in one poll enter focus-only chord lockout until all agent keys are up;
- threshold and exact accepted/focused result may arrive in either order;
- release before authorization cancels eligibility monotonically for that gesture;
- successful Space-down copies physical ownership out of projection-generation state;
- while active, no other key can acquire or inherit ownership;
- owner release emits up immediately; another held key must release and press again;
- boot, controlled reset, STOPPED, suspend, resume, disconnect/session loss, or HID failure clears candidate/owner and follows release-all/empty-first-report ordering.

Do not use `AgentProjection` pending storage as the active owner. `commitSnapshot()` clears pending focus state, which is correct for focus authority but wrong for a physical key that already owns Space.

## Shared patterns

### Gate before migration

Use the isolated feasibility environment and immutable manifest first. Production flags, discovery, udev, and gesture behavior move only after every applicable deterministic row and mixed stress pass on one exact deployment. A PASS closes transport exploration. Only the D-16 reproducible product REJECT may reopen another backend.

### One source for each truth

- `BoardAdapter` owns debounced physical down/release observations.
- `AgentProjection` owns exact binding/result correlation and ordinary focus feedback.
- `HoldController` owns local candidate cancellation and the global physical Space owner.
- `FixedSpaceHid` owns only report readiness/send/lifecycle mechanics.
- `UsbDeviceSession` owns exact application session sequencing and reconnect.
- Linux input observation is the external stuck-key oracle.

Do not copy any of these states into protocol payloads or a second UI cache.

### Immediate focus, delayed HID

Every occupied press keeps the current immediate focus intent. Space-down requires all of the following for the same gesture: exact accepted/focused result, threshold crossed from the latched physical edge, key still down, no monotonic cancellation, no chord lockout, no existing owner, and HID ready/send success. Either threshold or acknowledgment may arrive first.

### Release and lifecycle precedence

Clear local candidate/owner authority first. Then request or verify the empty HID report where transfer is possible. On unplug, observe Linux device teardown because no final report can be guaranteed. On mount/resume, require an empty report/state before rearming and require all agent keys up before a fresh gesture.

### Fixed authority boundary

The HID API exposes Space-down, release-all, and readiness only. The v2 schema remains the four existing product frame types. No keycode, text, macro, command, provider method, retry instruction, or hold authorization message crosses CDC.

### Existing presentation system only

Extend `RenderState`, the four current theme renderers, `LedEvents`, the four current grammars, and `LedEngine`. Focus failure and source fences preempt mic and active LEDs. Candidate and owner cues identify the physical key, not the currently focused pane.

### Allocation and timing bounds

Keep firmware state fixed-capacity. Use wrap-safe `uint32_t` elapsed/deadline comparisons. Poll/release work runs ahead of USB admission and rendering. Store distributions and raw traces on the host; firmware keeps counters and maxima only.

### Evidence is external and linked

Firmware logs cannot prove HID state. The gate must combine exact-pair application identity, USB descriptor/udev observations, bounded CDC counts, raw Linux input values, firmware metrics, lifecycle actions, framebuffer hashes, physical observations, binary hash, pairing digest, clean boot/session IDs, and immutable first-failure history.
