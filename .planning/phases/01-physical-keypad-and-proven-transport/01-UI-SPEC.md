# Phase 1 — UI Design Contract

> Visual and interaction contract for the host-driven guided bring-up utility and the four physical 128×128 keypad displays. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no existing UI system or application source exists |
| Preset | not applicable |
| Component library | none; use native terminal output/input on the Python host and the pinned official LILYGO display abstraction on firmware |
| Icon library | none; use bundled text glyphs and geometric primitives only, never a network or registry asset |
| Font | host: terminal-provided monospace; device: one locally bundled legible bitmap sans family with regular and semibold faces, no runtime font loading |

This is embedded firmware plus a temporary Python guided utility, not React, Next.js, or Vite. The shadcn initialization gate therefore does not apply. No existing tokens, components, CSS, or application UI were detected. The contract below establishes one Phase 1 visual language without implying a permanent product diagnostic surface.

### Surface and interaction model

- **Host is the narrator and evidence owner.** It shows exactly one current step, the expected physical observation, recorded device facts, and the available response. It never claims a physical result passed until the operator confirms it.
- **Keypad is the observed surface.** During a visual step, only the display, key, encoder action, or LED currently under test is highlighted. The other three displays show a quiet `WAIT` state; stale instructions are cleared before advancing.
- **One linear sequence.** The fixed order is Identify → Displays → Keys → Encoder → LEDs → Brightness → Reboot → Pair → Recover → Traffic → Selection. Completed steps remain summarized on the host, but the operator does not navigate among independent test tools.
- **Keyboard-first host control.** `Y` confirms the observation, `N` records a failure, and `R` repeats the current stimulus. Enter alone never confirms a physical observation. Any destructive replacement requires a typed word as specified under Copywriting.
- **No decorative animation.** State changes are immediate. A host-side spinner may update once per second only while detection or a bounded transport operation is active; device screens use static state labels.

## Spacing Scale

Declared values use only the standard 4-point set:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Device edge inset, glyph-to-label gap, thin status inset |
| sm | 8px | Device content padding, host inline gaps, separation between label and value |
| md | 16px | Host component padding, device separation between primary stimulus and instruction |
| lg | 24px | Host section padding and separation between instruction, evidence, and response areas |
| xl | 32px | Host major group gap; device minimum clear area around the active stimulus |
| 2xl | 48px | Host transition break between completed gate summary and next gate |
| 3xl | 64px | Device centered test-glyph footprint or host top-level sequence break only |

Exceptions: none. Borders are 4px when used as layout-bearing status rails; one-pixel hardware drawing primitives may render glyph strokes, arrows, and panel test outlines but must not be used as spacing tokens.

### Layout contracts

- Each 128×128 panel uses a 4px safe inset, leaving a 120×120 content box. Content must not touch the physical bezel.
- The device hierarchy is: 16px status label at the top, centered 24px test glyph or challenge in the middle, and at most two 12px instruction lines at the bottom.
- The host utility targets a minimum 80×24 terminal. At narrower sizes it must stop with the documented error rather than wrap prompts into ambiguity.
- Host text is left aligned. Device test glyphs and pairing challenges are centered; short status labels are left aligned inside the safe inset.

---

## Typography

Exactly four sizes and two weights are allowed:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | regular (400) | 1.5 |
| Label | 12px | semibold (600) | 1.25 |
| Heading | 20px | semibold (600) | 1.2 |
| Display | 24px | semibold (600) | 1.0 |

- Device text uses Label for state/instruction copy and Display for the unique panel number, arrow, percentage, or pairing challenge. Body and Heading are host roles.
- Host terminals that cannot expose font metadata preserve hierarchy through casing, spacing, and labels; they must not introduce a third weight or simulated italics.
- Device copy is uppercase and limited to short ASCII tokens (`WAIT`, `PRESS`, `TURN CW`, `PASS`, `FAIL`, `LINK LOST`) so missing glyphs cannot change meaning.
- Never rely on font size, weight, or color alone: every state has a literal label.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0F14` | Host background and device panel background |
| Secondary (30%) | `#1F2937` | Host step/evidence surfaces, inactive device regions, completed-step summaries |
| Accent (10%) | `#22D3EE` | Current-step left rail, active panel outline, pairing challenge, and requested control highlight only |
| Destructive | `#EF4444` | Failed observation, incompatible device, link-loss label, and destructive confirmation only |

Accent reserved for: the host current-step rail, the one physical observable currently being tested, the first-use pairing challenge, and the selected brightness sample marker. It must not color all prompts, all keys, completed steps, body links, decorative borders, or general text.

Supporting foregrounds are `#F8FAFC` for primary text and `#94A3B8` for secondary metadata. A passed step uses the literal `PASS` plus `#22C55E`; a warning uses the literal `CHECK` plus `#F59E0B`. These semantic colors occupy small badges/text only and do not replace the 60/30/10 surface distribution. Every colored state includes a text cue and, on device panels, a distinct geometric cue: outline for active, check for pass, cross for fail, and broken-link glyph for disconnect.

For display-color mapping, render red, green, blue, white, and black one at a time and name the requested color on the host. The operator confirms the observed color; firmware response is not visual proof.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Confirm observation` |
| Empty state heading | `No keypad detected` |
| Empty state body | `Connect the T-Keyboard S3 Pro with a data-capable USB cable, then retry detection.` |
| Error state | `Keypad link lost. Reconnect the paired keypad; this run will continue only after a new session is established.` |
| Destructive confirmation | `Replace this observation? The previous result for this step will be removed. Type REPLACE to continue.` |

### Required operational copy

| State or action | Exact language |
|-----------------|----------------|
| Start | `Start physical bring-up` |
| Awaiting operator | `Observe the keypad, then choose: [Y] Pass  [N] Fail  [R] Repeat.` |
| Physical pass | `Observation recorded as PASS.` |
| Physical failure | `Observation recorded as FAIL. Correct the issue or repeat this step before qualification.` |
| Candidate ambiguity | `Multiple compatible keypads detected. Disconnect other candidates and retry; no device was paired.` |
| Identity mismatch | `The connected keypad does not match the paired device. Reconnect the paired keypad.` |
| Incompatible protocol | `Incompatible protocol version. Flash the matching firmware and restart this run.` |
| Pairing challenge | Host: `Confirm that the keypad displays {CHALLENGE}. Type the challenge to pair this device.` Device: `PAIR` then `{CHALLENGE}` |
| Pairing success | `Paired with the physically confirmed keypad.` |
| Repeat stimulus | `Repeating this step; the prior result remains until you confirm a replacement.` |
| Traffic active | `Transport proof running — do not disconnect unless prompted.` |
| Traffic failure | `Transport proof failed. Evidence was preserved; review the recorded failure before rerunning.` |
| USB selected | `USB selected for v1: every frozen qualification gate passed.` |
| Wi-Fi branch eligible | `USB remains disqualified after documented remediation. The single Wi-Fi fallback may now be qualified.` |
| Selection blocked | `No transport passed the frozen qualification gate. Phase 1 is blocked; hybrid transport will not be used.` |
| Archive complete | `Bring-up evidence preserved. The temporary utility may now be archived.` |

Copy rules:

- Use direct verbs and name the affected object. Never use vague actions such as `Continue`, `OK`, or `Something went wrong` where confirmation, retry, or reconnect is intended.
- Distinguish `observed`, `recorded`, `acknowledged`, and `selected`; never translate a firmware acknowledgement into `PASS` without operator confirmation.
- Never show a transient `/dev/tty*` path as device identity. Show a bounded fingerprint such as `Device ••••7A2C`; full opaque identity belongs only in evidence.
- Error copy states the problem, the safe next action, and whether evidence was preserved. It never promises replay or automatic continuation for uncertain in-flight work.

## Component and State Contract

| Component | Required content | States | Interaction contract |
|-----------|------------------|--------|----------------------|
| Sequence header | `Phase 1 bring-up`, gate name, `step X of Y`, run ID suffix | ready, active, complete, blocked | Persistent on host; never becomes the action prompt |
| Current-step card | Specific physical action, expected observation, requirement source | waiting, stimulating, awaiting-confirmation, pass, fail | Only one active card; `Y/N/R` applies to its visible step ID |
| Evidence panel | Device/build facts, measured value, or `unavailable` | empty, populated, partial, preserved-after-failure | Read-only; unavailable facts are literal `unavailable`, never guessed |
| Response prompt | Explicit accepted keys and typed challenge where required | enabled, disabled-during-command, destructive-confirmation | Enter alone cannot pass; discard/replace uses exact typed confirmation |
| Host status banner | Problem plus recovery action | detecting, ambiguous, mismatch, incompatible, link-lost, blocked | Destructive red only for errors; focus remains on recovery input |
| Device test panel | Status label, unique stimulus, short instruction | wait, active, pass, fail, link-lost | Clear previous content before every state change; update one panel at a time through the official board abstraction |
| Physical-map stimulus | Panel number, top-edge arrow, requested color | display 1–4 active | Exactly one numbered panel active; host asks position/orientation/color separately |
| Input stimulus | `PRESS`, `TURN CW`, `TURN CCW`, or `CLICK` | armed, detected, operator-confirmed, failed | A raw event is displayed as detected but is not passed until operator confirms physical correspondence |
| Brightness sample | `BRIGHTNESS` and requested percentage | low, medium, high, confirmed | Present three bounded samples in order; do not imply persistence in Phase 1 |
| Pairing challenge | `PAIR` and short fixed-width challenge | awaiting-display, awaiting-entry, paired, rejected | Pair only on exact typed match and explicit physical confirmation; mismatch leaves binding unchanged |
| Traffic proof summary | elapsed/frozen duration, sent, acknowledged, rejected, latency, resource high-water marks | not-started, running, passed, failed, interrupted | Counters update in place; `passed` appears only after all frozen gates complete |
| Transport decision | selected transport and concise evidence basis | USB-selected, Wi-Fi-eligible, Wi-Fi-selected, blocked | Exactly one selected transport; no hybrid or automatic fallback state exists |

### State precedence

1. `incompatible`, `identity mismatch`, `ambiguous candidate`, and `link lost` override ordinary step content and disable confirmation.
2. `fail` preserves the failed evidence and keeps the current gate unresolved; it does not silently advance.
3. After reconnect, show `New session established` before returning to the unresolved step. Uncertain pre-disconnect work remains discarded.
4. A step becomes `pass` only after required machine evidence and explicit human confirmation are both present. Machine-only checks may say `acknowledged`, never `observed`.
5. The final selected-transport state is unavailable until the full frozen proof run passes. A USB failure exposes remediation, not a Wi-Fi toggle.

## UI Considerations

The post-verification probe classified 12 UI surfaces using the user-confirmed union of detected and missing element kinds. It raised 68 applicable element/category instances across the closed eight-category taxonomy. The resolutions below apply explicitly to every listed surface/category instance; none remain unresolved.

| Category | Element(s) | Status | Resolution |
|----------|------------|--------|------------|
| empty | current-step card, evidence panel, response prompt, device test panel, physical-map stimulus, brightness sample, pairing challenge, traffic proof summary | resolved (explicit) | Before discovery, show the existing `No keypad detected` copy. After sequence start, show `not started` or `unavailable` on host and `WAIT` on device; never render a blank panel or prompt. |
| loading | sequence header, current-step card, evidence panel, response prompt, device/media panels, input stimulus, brightness sample, pairing challenge, traffic proof summary | resolved (explicit) | Show the named bounded operation plus elapsed time; mark the current step `stimulating` or `running`, keep non-active device panels at `WAIT`, and disable confirmation until a stable result exists. |
| error | sequence header, current-step card, evidence panel, response prompt, device/media panels, input stimulus, brightness sample, pairing challenge, traffic proof summary | resolved (explicit) | Show the exact recovery copy in the host error banner, show `FAIL` or `LINK LOST` on device, preserve collected evidence, disable confirmation, and resume only after the documented recovery condition. |
| populated | current-step card, evidence panel, response prompt, device/media panels, brightness sample, traffic proof summary | resolved (explicit) | Render one active instruction with expected observation and response; show measured evidence as labeled rows; show one bounded device stimulus; update traffic counters in place; expose `PASS` only after machine evidence plus human confirmation. |
| partial | current-step card, evidence panel, response prompt, pairing challenge, traffic proof summary | resolved (explicit) | Preserve completed rows and failed evidence, label missing facts `unavailable`, keep the unresolved step visible, disable pass and advance, keep pairing unchanged on mismatch, and never show an overall `PASS`. |
| overflow | every bounded host/device text surface and list | resolved (explicit) | At terminals at least 80×24, wrap host prose within 80 columns and scroll prior evidence vertically; abbreviate displayed identity while retaining full evidence; on 128×128 panels accept only fixed bounded labels and challenges and reject unbounded host text. |
| zero-one-many | current-step card, evidence panel, response prompt, traffic proof summary | resolved (explicit) | Current-step and response surfaces render exactly one active item. Evidence and traffic show `not started` at zero, one explicitly labeled row at one, and multiple rows in fixed gate/counter order without changing spacing or hiding failures. |
| long-text | sequence header, cards, evidence, prompts, banners, device panels, pairing challenge, traffic proof summary, transport decision | resolved (explicit) | Wrap host prose within 80 columns; abbreviate visual device identity to a suffix while retaining the full opaque value in evidence; use only fixed short device labels and fixed-width challenges; never expand or clip the 128×128 layout with host-provided text. |
| physical-legibility (domain) | all four 128×128 panels | resolved (backstop) | `{ statement: "On the delivered unit, verify every text role and geometric cue at the lowest proof brightness and correct desk orientation, with no clipping or bezel collision.", verification: backstop }` |

## Registry Safety

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|
| shadcn official | none | not applicable — project is embedded C++/Python with no React/Next.js/Vite stack |
| Third-party UI registries | none permitted | not applicable — no registry code or remote UI assets may enter Phase 1 |

Registry safety is explicit: do not initialize shadcn, add registry manifests, copy registry blocks, fetch remote fonts/icons, or introduce a web component system for the temporary guided utility. The official pinned LILYGO board library is a hardware dependency identified by technical research, not a UI registry block; its source/revision gate remains governed by Phase 1 research. Any later proposal to add a third-party UI registry requires a new `view` plus source-diff safety review before it can modify this contract.
