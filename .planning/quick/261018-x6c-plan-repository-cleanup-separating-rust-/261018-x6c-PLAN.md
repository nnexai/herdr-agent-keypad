# 261018-x6c — Split Rust production runtime from Python diagnostics

## Outcome

- The only production runtime is the bundled Rust executable (`host/herdr_keypad/native`). No production code, test, CI step, or repo-owned current doc can launch or import the Python bridge package `herdr_keypad`. The one user-owned doc that still does (`.agents/skills/screen-capture-flow/SKILL.md`) is gated by G-SKILL. Without the owner's receipt, the outcome is reported as "implementation complete; user-owned docs blocked", not as a complete clean cutover.
- Retained device-facing Python is developer diagnostics only: screenshot capture, pairing (the only binding writer), exact-identity recovery checks, hardware-free self-checks, and verifiers for historical evidence under `tools/`. Separately, stdlib CI/release evidence utilities remain under `host/herdr_keypad/release/`; neither category retains the Python bridge.
- Every supported tool that opens the keypad serial port first holds **the Rust bridge's own authority lock** (`$HERDR_PLUGIN_STATE_DIR/bridge.lock`). This works as one lease. While a diagnostic holds it, any Rust `startup`/`start`/`restart` fails before it opens USB. The Rust stop path releases that lock only after it has closed the serial stream. This is a **cooperative same-user mutual-exclusion contract, not a security boundary** (D3a).
- The Rust parity tests consume the four checked-in Python-exported corpora as a frozen behavioral oracle. The corpus bytes stay unchanged, and their Python-source lineage is pinned as history. Rust does not become its own oracle.
- Historical evidence (`artifacts/`, `.planning/phases/`, `.planning/debug/`) is not modified.

## Decisions

**D1. The lease is the existing Rust authority lock.**
Diagnostics take `flock(LOCK_EX)` on the same `$HERDR_PLUGIN_STATE_DIR/bridge.lock`. fs2 0.4.3 on Unix uses `flock(2)` [INFERENCE: verify in Slice 1 step 1]. Because every Rust USB open requires that lock first (E4), holding it excludes every Rust path: the Herdr `startup` hook, `start`, `restart`, and in-process USB reconnects. Rust fails closed with no retry (E5, E8).
- *Rejected: a second, independent lease file.* Two locks can disagree, which is exactly how the XDG lock (E9) drifted out of sync.
- *Rejected: a "yield device" control request in Rust.* It adds a debug surface to production and violates RUST-07 and `production_surface.rs`.
- *Rejected: a documented "stop first" step only.* A later Herdr start can still race the port.

**D2. Fix the Rust stop ordering so lock acquisition proves the serial port is closed.**
On `Stop`, close the USB/Herdr boundaries first, then drop authority, then reply. Restart already does this. No new commands, protocol, or IPC. This is a correctness fix to the existing surface (E6).

**D3. One tools-side runner, `tools/keypad_lease.py`, holds the lease and passes it to a child as fd 9.**
The runner keeps the existing inherited-fd-9 contract, which is needed because PlatformIO upload and multi-step tools cannot take the lock themselves. It never stops or starts the plugin. The operator uses the Herdr `stop`/`start` actions. It never creates `bridge.lock`; it fails closed if the file is missing. That prevents a typo from creating a parallel lock.
- *Rejected: the runner calls `bin/herdr-keypad stop`.* That needs the full Herdr environment (`main.rs:58-69`) and would act on production lifecycle from a dev tool.
- *Rejected: automatic restart after release.* The operator restarts explicitly, so Herdr remains the only launcher.

**D3a. Cooperative contract, stated honestly.**
- **What the fd-9 guard checks:** `require_inherited_bridge_lock()` verifies that fd 9 refers to the validated state dir's `bridge.lock` by (dev, ino), and that it is not CLOEXEC. It then takes `flock(9, LOCK_EX|LOCK_NB)` and keeps holding the authority before any serial open.
- **What it does not check:** that this is the same lock object the runner took. `flock` on an fd that is unlocked but correct also succeeds and makes that process the lease holder. That case is still safe mutual exclusion against Rust, because Rust cannot start while the lock is held. It is an *unsupported standalone invocation*, not a proof that the lock was inherited.
- **Supported flow:** the supported CLI flow goes through `keypad_lease.py run`, because only the runner provides the wait timeout, the pre- and post- holder scans, process-group cleanup, and the verified release (D4b). Tools must never fabricate fd 9 or set the lease env vars themselves.
- **Out of scope:** the guard does not authenticate the runner (no PID or nonce check) and does not defend against malicious same-user code. Strict runner-only enforcement would need a separate design and is not required for this cleanup.

**D3b. Invocation convention.** `tools/keypad_lease.py` is always run by the diagnostics venv interpreter, because it imports `phase1_bringup`. It gets no shebang requirement and no executable bit. Every example uses:

```bash
PY=tools/phase1_bringup/.venv/bin/python3
LEASE="$PY tools/keypad_lease.py"
```

These are written as `$LEASE locate`, `$LEASE run …`, and `$PY tools/capture_panel.py …`. The new file follows `capture_panel.py`'s `sys.path` insertion pattern (`capture_panel.py:8-9`).

**D4. The state directory comes from the running bridge, not from a guess.**
`$LEASE locate` reads `HERDR_PLUGIN_STATE_DIR` from `/proc/<pid>/environ`, for same-uid processes whose `/proc/<pid>/exe` resolves to `<plugin-root>/bin/herdr-keypad`. The plugin root defaults to `~/.local/share/herdr/plugins/herdr-keypad` (the observed installed path). `locate` requires exactly one distinct value. It works **only while the bridge is running**, so the operator caches the value before stopping: `STATE_DIR="$($LEASE locate)"` → Herdr `stop` → `status` stopped → `$LEASE run --state-dir "$STATE_DIR" -- …`. No example calls `locate` after the stop. `run` also accepts `HERDR_PLUGIN_STATE_DIR` from the environment.
After the lease is acquired, the runner scans same-uid `/proc/*/fd` for the exact candidate device nodes. If any process holds one open, it fails closed. This also catches a wrong `--state-dir` while Rust is running.

**D4b. "Released" means independently verified, not "our fds closed".**
A descendant can escape the process group with `setsid` and still hold the inherited fd 9, which keeps the flock, or keep the tty open. Group-kill alone is therefore not proof. After cleanup, the runner closes all of its own copies of the lock. It then opens `bridge.lock` again on a fresh open file description and tries `flock LOCK_EX|LOCK_NB`, and repeats the device-holder scan.
- It prints "lease released" and exits with the child's code only when both checks are clear.
- If either check fails, it exits non-zero with the holder pids and never prints a success line.
- A failed release is fail-safe: Rust cannot start while an escaped holder keeps the flock. The device-holder failure is the unsafe case, and it is reported, not hidden.
- No cgroups or `systemd-run` scoping (rejected as scope expansion).
- Residual risk: a non-lease-aware escaped process (for example a stray `esptool`) could open the tty after the final scan. Bounded by the scan plus the documented operator check (`fuser` on the device) before Herdr `start`.

**D5. Freeze the oracle.**
- Keep the four corpora byte-identical and pin their file SHA-256 values in Rust.
- Replace the live source hashing with a pinned historical lineage table of the 11 recorded hashes. Recorded values are checked against the pinned table, not against files.
- Delete the exporter, the byte-compare test, and the environment-root test.
- Before deleting anything, prove once (Batch 0) that the current exporter still reproduces the corpora byte for byte.
- *Rejected: re-homing the Python bridge under `tools/`.* That keeps a second Python bridge.
- *Rejected: regenerating fixtures from Rust.* Rust would become its own oracle.
- *Rejected: stripping `sources` from the fixtures.* That rewrites proof and changes the hashed release inputs (E16).

**D6. Detach the bridge-coupled modes of `phase3_smoke.py` by deleting them, not relocating them.**
The modes that drive the device through the Python `UsbDeviceSession`, `bridge` types, or `--run-bridge` act as a second host bridge. Phase 5 acceptance must use the real installed stack (E20), so these fixture-publishing controllers are not a Phase 5 workflow. Hardware-free validators for committed historical evidence stay.

**D7. Route every retained serial open through one helper.**
`serial_link.open_leased_serial()` calls `require_inherited_bridge_lock()` and then `serial.Serial(..., exclusive=True)`. Historical device commands stay runnable but cannot bypass the lease. Retiring them is out of scope (see Q3).

**D8. Live capture of the `current` scene happens after the Rust stop.**
It shows whatever the firmware renders once the host session has ended. [INFERENCE] The firmware's post-session rendering is not established and is recorded as a device observation. Deterministic `--theme/--scene` captures remain the primary visual regression tool. There is no Python snapshot publisher (Python `--smoke` is removed).

**D9. Layout.**
Change no paths except: add `tools/keypad_lease.py` and `tools/README.md`, and delete the two Python bridge directories. `tools/phase1_bringup` keeps its name and venv because many retained paths depend on it (`__main__.py:196-203`, `evidence.py:356`).

**D10. Requirements amendment.**
Amend the current RUST-07 and RUST-08 wording in `REQUIREMENTS.md` in place. Add a dated note that cites 261018-x6c. Keep both checkboxes complete. Do not edit 04-CONTEXT, 04-VERIFICATION, ROADMAP Phase 4 text, or artifacts. Their "Python oracle 37/37" and "70/70" counts stay as true history. The amended RUST-07 names both retained Python roles: developer diagnostics under `tools/`, and stdlib-only CI/release evidence tooling under `host/herdr_keypad/release/`. Neither may import a bridge.

  - **Recommendation:** (b) is accepted, but `run` always performs the post-acquire `/proc` fd scan (D4). `locate` is offered as the safe way to learn the path.
